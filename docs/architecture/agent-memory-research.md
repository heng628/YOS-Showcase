# Agent 记忆与学习能力 · 调研纪要（SOTA + 产品实践 + 技术栈）

- 日期：2026-08-25（调研三路并行：记忆架构 / 产品实践 / 本地技术栈）
- 目的：为「YOS Agent 的记忆力与学习能力」方向性设计提供事实依据（brainstorming 调研阶段）。
- 结论状态：**调研结论（非设计决策）**；设计按 brainstorming 流程逐节确认后另出规格。

---

## 1. 核心结论（先行）

> **不要让 LLM 自维护整库记忆；走「确定性优先 + 分层混合」：** 写路径由程序确定性记录（结构化事实/事件日志，可审计可回放），LLM 只在读路径做摘要/解释/建议。检索以「结构化 + 图」为主、向量为辅（仅在理解/建议阶段兜底语义召回）。这与 YOS 既有原则一致（LLM 不做确定性计算、永不生成 SQL、Proposal→确认、Activity Log 全覆盖）。

## 2. SOTA：Agent 记忆架构（2025–2026）

- **主流框架**（只作参考，勿整套引入）：Mem0、Letta（MemGPT）、MemOS、Zep/Graphiti（时间知识图谱）、LangMem、A-MEM、Cognee——共性分层：工作记忆 / 情节记忆 / 语义记忆 / 程序记忆；差异在存储介质（向量库/知识图谱/结构化表）、写策略（LLM 判定重要性 vs 程序化）、衰减与整合（consolidation/decay）。
- **上下文工程（不臃肿）**：分层注入（系统/用户/资产语义/画像）、会话摘要压缩、只检索相关、token 预算、后台固化——"agentic context engineering" 2025–2026 的核心就是**把上下文当预算管理**。
- **不失忆的关键机制**：持久化存储 + 记忆固化（关键事实提升为画像）+ 重要性/新鲜度评分 + **冲突消解与来源校验**（OWASP AISVS 8.2.3：agent/tool 输出须经来源校验才可入可信记忆；arXiv 2606.01435 / engram·memore 类"无 LLM 写路径"是成熟先例）。
- **评测基准**：LOCOMO、MemBench、AgentMemBench、EvoMemBench——结论普遍：LLM 自发记忆能力薄弱且不稳，**外部持久记忆是必需品**。
- **风险（已证实）**：纯 LLM 自维护记忆 → 过度概括/漂移/**把推断当事实**（manufactured confidence）；记忆污染（memory poisoning）从坏输入腐蚀整库。

## 3. 产品实践与用户感知

- **两范式**：显式可控（Claude memory 2025-10 起支持用户直接编辑；Cursor rules）vs 自动隐式（ChatGPT Pulse 自主召回；Windsurf Cascade）。共识：显式=可控但靠维护；隐式=省事但易污染难审查。
- **用户两极**：喜欢「被理解、不用重复」；反感「记忆污染」（错记 3 件事一周）、**被监视感**（无提示叫出名字 = creepy；Gemini Spark 被批评）、「AI 忘了」、**删了仍被召回**（ChatGPT 被爆料删除的记忆多年后被召回）。
- **学习信号先例**：推荐系统把「跳过/不喜欢」建为负反馈（ACM/IEEE）；Gmail 靠「举报垃圾/非垃圾」训练。——**隐式学习的代价 = 必须配可见/可编辑/可删除的记忆面板**（Claude 为范本）。
- **给 YOS**：记忆「可见、可删、可纠正」；外显 = 高置信度一次一条（惊喜 vs 透明的平衡，避免"监控面板"观感）；起点信号 = 拒绝/忽略/删除（负向，天然契合 §31.8「拒绝后不再重提」）+ 常用指标（正向）；信号只沉淀为**偏好证据**，绝不据此擅自执行（回落到 Proposal→确认）；「本地优先 + 一键清空」= 最大信任差异化。

## 4. 本地技术栈（详见 `agent-memory-stack-research.md`）

- **最小可落地（S1）**：SQLite（沿用 better-sqlite3+Drizzle）关系表 `memories(kind, subject, predicate, object, value, source, confidence, valid_until, ts)` + **FTS5** —— 零新增依赖、近零体积。
- **完整版（V1+）**：+ `sqlite-vec`（**用活跃 fork：stacklok/photostructure**；原 asg017 仓库已停滞）+ 混合 embedding：**在线顺带云嵌入（随 LLM 调用）**、离线降级本地 MiniLM（transformers.js ONNX，~20–25MB 量化）。
- **图谱**：仅在多跳推理（依赖链）确需时引入「关系三元组」（RDF 风格存 SQLite）；常规场景关系表足够。
- **不建议**：LanceDB/FAISS/Chroma（原生绑定/体积/臃肿，小体量杀鸡用牛刀）；DuckDB VSS 仅当需要向量+分析一体时再评估（版本敏感）。
- **先例**：Obsidian Copilot（宿主数据 + 外来索引）、AnythingLLM（SQLite 元数据 + 可插拔向量库——抽象层要可插拔）。

## 5. 设计约束（调研 → 设计）

1. 记忆是**产品领域对象**（用户级），不是外部框架的子模块；不引入 Mem0/Letta 等重依赖。
2. 写路径确定性优先（事件/事实），LLM 只做读路径抽象——**防污染、防幻觉、可审计**。
3. 读取分层注入 + token 预算 + 摘要压缩——**防上下文臃肿**。
4. 持久化 + 固化 + 冲突消解——**防失忆**；证据可追溯、画像可重算。
5. 用户可见、可编辑、可删除、一键清空、删除永不再召回——**防翻车**（对应 product-side 最大教训）。
6. 隐私：本地权威（用户数据侧记忆全本地）；**云端只放"能力面"（ADR 001：长期 AI Profile 本就规划在云端能力面）与运行时服务**——这一条直接决定下面的"粘性设计"。
7. 记忆 ≠ 项目记忆系统（docs/memory 是开发 YOS 的 AI 用的；产品内 Agent 记忆是 YOS 用户的）——**两者不得混建**（AGENTS.md §32 红线）。
